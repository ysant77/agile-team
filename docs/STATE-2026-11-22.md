## 4a. Fixes from the review of 23 Nov

Each fix is its own pull request; this list says what each one changes.

**Merged, not deployed.** PRs 65 and 66 are on `main`, but the development site still runs 5.8.0
from b47118e. The deploy that puts them live needs the owner's word; no deploy was made.

- **GitHub errors** (PR 65). Each GitHub failure has its own reason:
  rate limit and secondary limit (both with the time to try again), 401, 403 with calls left,
  404, server error, network error. Server and network errors are tried 3 times; a secondary
  limit of at most 10 s is waited out once. A transient failure (the two limits, a server or
  network error after the retries) is not a verdict: the work item gets a "was not checked"
  comment with the time to try again, nothing is stored, and the claim's slots are given back.
  The 403 of the video run (audit entry 27) would now be either a "not checked" comment (if it
  was the rate limit) or a stored Cannot verify that says the token or app may not read the
  repository. The token is sent on every GitHub path (claims, reviews, cases, discovery, the
  commit spike). One claim reads the PR file list once (about 10 calls for a merged PR, not 12).
  Stated limit: a "not checked" result writes a log line only. It leaves no audit entry, so the
  audit chain does not show that the claim was made and not checked; the work item comment does.
- **No ACs** (PR 66). A plain work item (no ACs, no sub-tasks) with `claim: done` gives Cannot
  verify, not Contradicted. Regression on sets 1 to 5: only B13 changed, from contradicted to its
  predicted cannot_verify.
- Limits with no code fix: V02 and V09 of set 5 (unsafe Supported) and V13 (a false block). In
  all three the answer depends on what the AC text means, and the verifier never reads AC text. A
  "Supported" means the named test fails on base and passes on the head, and that the other checks
  pass; it does not mean the test covers every case of the AC. The panel says so.
